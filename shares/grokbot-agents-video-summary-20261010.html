怎么把对编程 Agent 的信任爬上去：验证闭环、技能与硬约束

Cursor 工程师 Lauren 分享：别急着开一百个 Agent；先建「能自己跑起来验对错」的技能与护栏，信任上去了，才能并行、上云，甚至让 Agent 自动合并 PR。

讲者与场景

这是一场约 55 分钟的英文访谈/分享（主持人 Colin）。讲者 Lauren 大约五个月前加入 Cursor，先参与 Agent Window（内部代号 Glass，React 应用）的性能与交付，后来也谈到自家新产品 GrokBot 以及一套偏「给 Agent 写代码」的架构（代号 Dune）。现场有屏幕分享：信任曲线图、验证技能、feature map、Bug 复现 Agent「Benny」、以及 GrokBot/CI 相关界面。X 上西班牙文宣传写「SpaceXAI 工程师带 20+ GrokBot Agent」——视频正文主要讲的是 Cursor 侧工程实践与信任曲线；讲者在问答里提到 Cursor 与 SpaceX AI 在「成本–智能」权衡上的优化，但并未展开个人是否运行「20+ Agent」的细节。

核心论点

  • AI 最好当结对编程伙伴，而不是外包思考或盲目「vibe coding」冲产量。
  • 核心问题不是「会不会写代码」，而是「你信不信它」：不信任就会变成人肉微管理，省下的写码时间全花在审查与纠错上。
  • 信任曲线要爬：先紧盯少量本地 Agent → 验证闭环稳住正确性 → 再扩到云端并行与自动化；没有捷径，跳级只会烧 token。
  • 工具箱里最重要的是 verification（验证）：让 Agent 自己真正跑应用、打性能追踪、开模拟器等，闭环测「对不对」，不等于保证「写得好」，但能先保证「写对了」。
  • 把失败模式沉淀成 skill（技能，多为 Markdown 指令）：观察工具调用与思考过程，看到幻觉就立刻补一条「别猜、去搜代码」类规则。
  • 要大规模自动化，还得改造代码库：用硬约束（CI/静态分析/架构约定）把「最短捷径」变成「正确捷径」，软规则（rules/Bugbot）只能当辅层。
  • GrokBot 这类产品把 Agent 做成「像 iMessage 里的人」，让产品/设计/GTM 也能在硬护栏下直接改功能、修 bug。

信任曲线（为什么→所以）

刚开始用不熟的 Agent 时，你几乎不信它，因为你会看到它乱猜、幻觉、自信地指错病因；所以你会盯着每一个输出、自己当验证器（打开本地构建、贴截图、贴报错），于是人成为瓶颈，几乎没法并行——因为连一个都不信，就更不敢开一百个。后来 Lauren 花约五个月，把「验证技能 + feature map + eval（评测）+ 硬 CI」叠上去：因为 Agent 能自己复现、自己验、技能也用 eval 测过，所以你才敢把工作放到云端（例如 Benny 自动复现用户反馈），再往上甚至允许 Agent 自动合并 PR，人早上起来在 main 上抽查。因为信任是个人工程品味的累积，所以不能从「本地盯梢」直接跳到「上千云 Agent」——那样又贵又乱。

可复用做法

Verification 技能（让 Agent 自己验）

为什么：没有它时，人是唯一验证器，Agent 写完你还要本地跑、贴截图，无法并行。

怎么做：教 Agent 用 Chrome DevTools Protocol、iOS 模拟器等真正打开应用、跑性能 trace/heap snapshot，像用户一样操作并确认是否修好。

视频例子：为 Agent Window（Glass）做的 Control Glass 技能：Agent 能拉起窗口并采性能追踪，而不只靠你贴火焰图截图瞎猜。

Feature map（功能地图）

为什么：光会「操控 UI」不够；Agent 不知道侧栏、PR 页等功能在哪，就会在界面上乱点、空转。

怎么做：维护一份地图：用户视角怎么走到每个功能、快捷键、以及用 CDP 选中 DOM 的属性；并有创建/Maintain verification skill 保持更新。

视频例子：Slack 里常有「一张截图 + 三个问号」的烂反馈；有 feature map 后，Agent 更容易把模糊报告映射到具体界面路径。

P-Stack（PSTAC）插件与增量技能

为什么：技能不是一开始就写全的；要从真实失败模式里长出来。

怎么做：名字梗来自 Gary Tan 的 G-Stack（讲者姓氏也类似，自称 Potato Stack）；从 Control Glass、HAL（逼 Agent 真读代码、用子 Agent、别猜）等一点点加；可用插件里的 create verification skill 帮你搭类似体系。

视频例子：早期 Agent 自信「就是这个 bug」，但工具调用显示根本没读该读的文件——于是写成 HAL 类技能。

Eval = 给技能做单元测试

为什么：产品在变，技能会过期；要知道改完的技能是否真的更好。

怎么做：协调 Agent 写评分量表，生成子 Agent 任务（目录名故意不暴露「这是评测」，以免 Agent 改变行为）；跨多种模型跑；可用 slash loop 把分数「爬坡」到目标；另用不同模型当 judge 防偏。

视频例子：P-Stack 的 potato mode 下有 eval playbook；每次改技能就跑一遍。

先本地观察，再上云放大

为什么：本地看得见 Agent 怎么点界面、怎么调 API；云端适合把已信任的闭环扩成全员自动化。

怎么做：验证技能先在本地盯行为；环境配好后，同一套技能给 Cloud Agent 用，整队受益。

视频例子：Benny：接用户反馈 → 云桌面开 Cursor → 用同一套 control/verification 技能复现；有时发现「main 上已修好，只需发新版本」。

Dune 架构：给 Agent 的硬护栏

为什么：纯 vibe 出来的绿野（greenfield）没有护栏，Agent 会专走捷径，代码库会失控；大厂那套「防最弱工程师」的约定反而适合 Agent。

怎么做：功能按目录共置；Electron main/renderer 分目录并用依赖图 CI 禁止乱 import；禁用 React useEffect、甚至禁止多数代码注释（Agent 爱写过时/误解历史的注释）；原则是「最短路径 = 最佳路径」。软层 rules/skills/Bugbot 仍保留，但不单独依赖。

视频例子：讲者称对 GrokBot 做了大量重构（提到约 600+ PR 量级的投入叙述），之后有时醒来已有约 20 个 PR 被 Agent 合入，人在 main 上复查；PR 大小从几十行到上千行不等，鼓励拆成原子 PR 方便回滚与读历史。

把 Code Review 抱怨变成硬规则

为什么：靠人逐条评论维持不变量，是反模式；人一走开代码库就会烂。

怎么做：每次想在 PR 上写「别这么做」，就问：能变成 lint、CI 失败，还是从架构上消灭这类问题？

视频例子：Agent Window 仍常因进程隔离差导致重活跑进 renderer、掉帧；计划把 Dune 类学习迁回去。

代理角色 / 舰队

  • 本地结对写码的少量 Agent（早期高信任成本、人全程在环）
  • 带 verification / Control Glass 的验证型 Agent（自己跑应用与性能）
  • 协调 Agent + 评测子 Agent + 跨模型 Judge（维护技能质量）
  • 云端 Benny：自动接反馈、复现 bug、对照 main 是否已修
  • 可自动开 PR、在护栏足够时自动合并的编码 Agent
  • GrokBot 里带身份/名字的多个 Agent：可按账号或职责编排；PM 可用 Agent 汇总某人昨夜提交，非工程师也可在约束下修 bug/加功能

演示与界面

  • 手绘/示意图：信任曲线——在环深度 vs 可并行 Agent 数量；并对照加入 Cursor 后贡献量上升
  • Agent Window（Glass）相关：Chrome 性能火焰图、验证技能与 feature map 文件结构
  • P-Stack 插件：create/maintain verification skill、eval playbook（potato mode）
  • Benny 云端复现用户报告的流程界面（含「已在 main 修复」类结论）
  • GrokBot / Dune：功能目录约定、Electron main vs renderer 分隔、严格 CI/Bugbot 层

金句（意译）

  • 最好的用法是结对编程，而不是外包你的思考。
  • 不信任 Agent，就像不信任下属——你只会陷入微管理。
  • 验证不保证写出「好代码」，但能先逼出「正确代码」。
  • 你不能还不信任一个 Agent，就去开一百个。
  • 技能像把高中生工程师教熟：用高质量指令把模型「拽」到更聪明的模式。
  • 工程师越来越像主厨：搭厨房、分站、下任务，而不是每道菜亲自炒。
  • 最短路径就该是最佳路径——因为 Agent 天生爱抄近路。
  • 人肉 Code Review 维持的规矩，是代码异味；要把它变成硬失败。
  • GrokBot 像非技术同事的「Cursor 时刻」：界面像 iMessage，Agent 像一个个有名字的人。

你可以带走的行动

  • 先做一件事：让 Agent 能自己把应用跑起来并验证结果，而不是只会生成补丁。
  • 给产品写一份 feature map（怎么点到每个功能 + 选择器），再谈自动修 bug。
  • 每次 Agent 翻车，记一条失败模式 → 写成 skill；用简单 eval 回归，别凭感觉改提示词。
  • 信任够了再上云、再并行；别为了「看起来很 AI」空烧 token。
  • 投资硬约束（lint/CI/架构边界）优先于再写一份风格指南；软规则只能叠在硬层上面。
  • 绿野项目更危险也更值得提前立规矩；已有大厂级护栏的棕地反而更适合 Agent。
  • 若你在做产品/设计：可试「聊天式多 Agent」工具，但交付仍应落在有 CI 护栏的仓库上。

局限与注意

  • 讲者明确说自己在 AI 实验室有「近乎无限 token」——普通人应按 ROI 裁剪，不能原样复制吞吐数字。
  • 「上千 PR / 自动合并」是讲者个人路径与仓库护栏成熟后的结果；视频也承认外人会合理质疑代码质量，关键在于你是否真的建好验证与硬约束。
